# Django Basics & Project Architecture

## What is Django?
Django is a high-level Python web framework that encourages rapid development and clean, pragmatic design. It follows the "batteries-included" philosophy, meaning it comes with built-in features for things like database management, authentication, and security, so you don't have to build them from scratch.

In this project, Django is used specifically as a backend API (likely using Django REST Framework) to serve data to the Next.js frontend.

## The Core Concepts (MVT Architecture)
Django traditionally follows the Model-View-Template (MVT) architecture. However, because you are using Next.js for the frontend, Django acts purely as an API, modifying the pattern to Model-View-Serializer:

1. **Models (`models.py`):** 
   This is the single, definitive source of information about your data. It contains the essential fields and behaviors of the data you're storing. Each model maps to a single database table. When you change models, you create "migrations" (in the `migrations/` folder) to update the actual database to match your Python code.

2. **Serializers (`serializers.py`):**
   Since the Next.js frontend communicates via JSON over HTTP, you cannot send raw Python objects. Serializers translate complex data types (like Django model instances) into native Python datatypes that can then be easily rendered into JSON. They also validate incoming JSON data from the frontend before saving it to the database.

3. **Views (`views.py`):**
   This is where the core logic happens. A view receives a web request (e.g., GET /cases/ or POST /documents/), interacts with the models to retrieve or save data, uses serializers to format it, and returns a web response (usually a JSON response).

4. **URLs (`urls.py`):**
   This is the routing mechanism. It maps specific URL patterns (like `/api/cases/`) to the specific view functions that should handle the request.

## How We Are Managing Things in This Project
Looking at the `backend/api` directory, the project uses an advanced, structured approach (Service-Oriented Architecture):

1. **Permissions (`permissions.py`):** Handles Role-Based Access Control (RBAC). It checks if the user making the request has the right authorization (e.g., is the user an Admin or standard Investigator?) before letting the view execute.

2. **Services (`services/`):** Business logic is often decoupled from views. Instead of putting massive chunks of calculation or complex logic directly in `views.py`, it is moved to service functions. This makes the code easier to test and reuse.

3. **Repositories (`repositories/`):** This is a pattern used to abstract database queries. Instead of writing complex `Model.objects.filter(...)` queries directly in the view, they are placed in repository files. This keeps the database logic separate from the HTTP response logic.

4. **Schemas (`schemas/`):** Often used for standardizing data structures or validation, keeping input/output definitions clean.

## The Most Important Concepts
- **ORM (Object-Relational Mapping):** You don't have to write raw SQL queries. You interact with the database using Python classes (Models), and Django translates that into SQL securely.
- **Migrations:** The tracking system for database changes. You run `python manage.py makemigrations` to generate files that describe your model changes, and `python manage.py migrate` to apply them.
- **Authentication & Security:** Django handles user sessions, password hashing, and protection against common vulnerabilities (like CSRF and SQL injection) out of the box.
